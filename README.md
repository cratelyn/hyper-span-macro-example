# thoughts on linting `hyper::trace`

this repository exists to provide a playground for exploring solutions related
to hyperium/hyper#4231. for more information on work related to strict linting
in hyper, see hyperium/hyper#4071.

## macros

hyper contains a `trace` submodule, introduced in hyperium/hyper#3326,
that contains macros like the following:

```rust
macro_rules! trace {
    ($($arg:tt)*) => {
        #[cfg(feature = "tracing")]
        {
            tracing::trace!($($arg)+);
        }
    }
}

macro_rules! trace_span {
    ($($arg:tt)*) => {
        {
            #[cfg(feature = "tracing")]
            {
                let _span = tracing::trace_span!($($arg)+);
                _span.entered()
            }
        }
    }
}
```

these thinly wrap `tracing`'s macros, to account for the fact that tracing
support in hyper is opt-in. it is gated behind a feature flag, and
additionally mandates that the `hyper_unstable_tracing` flag be enabled.

however, this leads to violations of clippy's `let_unit_value` rule when
compiled without the `tracing` feature flag is enabled. this is because
`trace_span!` only returns a `tracing::span::Entered` when that flag is active,
otherwise it returns `()`.

this repository outlines some possible solutions to this issue.

### [`d601a04`](https://github.com/cratelyn/hyper-span-macro-example/commit/d601a04e6b50826d3753933997b27d55345654a8) conditionally allow `let_unit_value`

this is one way we could go about solving this issue, by conditionally
applying an attribute allowing violations of the `let_unit_value` to our
binding.

clippy is now satiated with and without the tracing feature active:

```text
; just check
cargo clippy --no-default-features
    Checking hyper-span-macro-example v0.1.0
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.03s
cargo clippy
    Checking hyper-span-macro-example v0.1.0
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.04s
echo 'looks good!'
looks good!
```

this is not great, however. we solve the linter warnings like so:

```rust
 #[cfg_attr(not(feature = "tracing"), allow(clippy::let_unit_value))]
 let _entered = trace_span!("instrumented");
```

applying attributes to expressions is still a nightly feature we cannot rely on
yet, so call-sites for our macros must be updated rather than modifying the
code generated by the macro. see rust-lang/rust#15701.

`#[cfg_attr]` is a bit esoteric, and if we require that instrumenting code in
hyper require this song and dance every time we create a span, it will
generally discourage instrumentation.

## [`b765f5f`](https://github.com/cratelyn/hyper-span-macro-example/commit/b765f5f3256b6f78e2e760fe8acdfd66209421eb) define a "disabled" raii guard

this commit demonstrates another workable solution: define an inert RAII guard
to stand in place of a tracing span guard when the `tracing` feature flag is
not enabled.

now, the `trace_span` macro looks like this:

```rust
macro_rules! trace_span {
    ($($arg:tt)*) => {
        {
            #[cfg(feature = "tracing")]
            {
                let _span = tracing::trace_span!($($arg)+);
                _span.entered()
            }
            #[cfg(not(feature = "tracing"))]
            {
                crate::trace::DisabledGuard {}
            }
        }
    }
```

note the additional block with a `#[cfg(not(feature = "tracing"))]` predicate.

the pleasant benefit of this is that it does not require call-sites to decorate
the `let _entered = trace_span!("instrumented")` statement with a configured
attribute.

with this inert guard type, these expressions are not being conditially
compiled to either `()` and `tracing::span::Entered`. instead, they are both a
guard of some sort.

this seems like a more ergonomic solution. we can address these linting issues
internally!
